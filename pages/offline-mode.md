# Офлайн-режим

Офлайн-режим дає змогу компʼютеру каси, на якому встановлено Device Handler, працювати без інтернету та за недоступного сервера Fitshandler. Операції, виконані без звʼязку, передаються на сервер після відновлення звʼязку.

## Пристрої й доступ

### Увімкнення на компʼютері

- Офлайн-режим вмикається окремо для кожного компʼютера каси.
- Увімкнути офлайн-режим може користувач з роллю **Супер Адмін** або **Адмін**, який увійшов у систему на цьому компʼютері. Користувач з роллю **Менеджер** отримує відмову `403`.
- Під час увімкнення компʼютер отримує доступ пристрою — окремий ключ, привʼязаний до студії, користувача й компʼютера.
- Ключ передається компʼютеру один раз. Сервер зберігає лише його хеш; відновити ключ за даними сервера неможливо.
- Для одного користувача на одному компʼютері діє один доступ пристрою. Повторне увімкнення видає новий доступ, попередній припиняє діяти.
- Доступ пристрою відкриває лише обмін даними офлайн-каси із сервером: передавання офлайн-операцій і отримання даних каси. Інші розділи системи за доступом пристрою недоступні.

### Строк дії доступу

- Доступ пристрою діє 7 днів від останнього звʼязку компʼютера із сервером, а не від дня увімкнення.
- Кожне звернення компʼютера до сервера продовжує строк на 7 днів від моменту звернення. Компʼютер, який звертається до сервера щодня, доступу не втрачає.
- Компʼютер, який не звертався до сервера понад 7 днів, втрачає доступ. Офлайн-режим на ньому потрібно увімкнути повторно за наявності звʼязку.
- Доступ припиняє діяти, якщо користувачу, для якого його видано, знято роль із доступом до системи.

| Параметр | Значення |
|---|---|
| Строк дії доступу | 7 днів від останнього звʼязку |
| Оновлення строку | не частіше одного разу на 5 хвилин |
| Чинних доступів на користувача й компʼютер | 1 |

### Список пристроїв і відкликання

- Список пристроїв розміщено в розділі **Налаштування** на вкладці **Пристрої**. Вкладку бачать лише користувачі з роллю **Супер Адмін** або **Адмін**; користувач з роллю **Менеджер** її не бачить.
- Список містить чинні доступи пристроїв у колонках: **Назва пристрою**, **Користувач**, **Останній звʼязок**, **Дата увімкнення** (дата й час увімкнення офлайн-режиму на компʼютері), **Доступ діє до** (дата й час завершення строку дії доступу).
- Дати й час у колонках **Останній звʼязок**, **Дата увімкнення** і **Доступ діє до** показуються в часовому поясі студії, незалежно від часового поясу компʼютера, на якому відкрито список.
- Якщо компʼютер ще не звертався до сервера після увімкнення офлайн-режиму, у колонці **Останній звʼязок** показується «Ще не виходив на звʼязок».
- Якщо чинних доступів немає, показується «Немає пристроїв з увімкненим офлайн-режимом».
- Кнопка **Відкликати** відкриває вікно підтвердження. Після підтвердження доступ пристрою припиняє діяти негайно, показується повідомлення «Доступ пристрою відкликано», список оновлюється. Якщо сервер не відкликав доступ, повідомлення про відкликання не показується, список оновлюється. Наступне звернення компʼютера із цим доступом отримує відмову; офлайн-режим на ньому потрібно увімкнути повторно.
- Кнопка **Відміна** у вікні підтвердження закриває вікно без змін.
- Відкликаний доступ і доступ зі строком, що минув, у списку не показуються.
- Якщо список не вдалося отримати, список порожній.

| Звернення з доступом пристрою | Відповідь сервера |
|---|---|
| Доступ відкликано, строк минув або в користувача немає ролі з доступом | `401` |
| Розділ, який доступ пристрою не відкриває | `403` |
| Дані іншого компʼютера, ніж той, для якого видано доступ | `403`, код `DEVICE_MISMATCH` |

## Які дані доступні без інтернету

Офлайн-каса працює з даними, отриманими від сервера під час останнього звʼязку. Плашка офлайн-режиму показує час отримання даних: «Дані станом на …».

### Склад даних

| Дані | Що передається |
|---|---|
| Абонементи | усі абонементи студії з ціною, кількістю занять і строком дії |
| Категорії | усі категорії занять |
| Товари | назва, ціна, залишок |
| Тренери | імʼя, колір, категорії; телефон і дата народження не передаються |
| Зали | назва, місткість |
| Тренування | шаблони регулярних занять, чинні у вікні розкладу, і разові заняття вікна розкладу |
| Клієнти | імʼя, прізвище, тип, номер картки, відпустки (заморозки), баланс особового рахунку й час останньої операції за рахунком; телефон, email і дата народження не передаються |
| Абонементи клієнтів | активні, ще не активовані й заморожені абонементи, зокрема спільні абонементи мережі студій, із залишком занять, кількістю занять на початку абонемента (`initialWorkouts`) і строком дії; завершені абонементи не передаються |
| Борги | неоплачені борги із загальною сумою (`totalAmount`), залишком до сплати (`remainingAmount`), складом і клієнтами; залишок до сплати дорівнює залишку на екрані боргів клієнта |
| Сертифікати | лише активні сертифікати з чинним строком дії: номер, опис, ціна, абонементи сертифіката, строк дії, клієнт, статус |
| Продажі | продажі й поповнення особового рахунку від початку доби 3 дні тому за часовим поясом студії, крім продажів поточної онлайн-зміни: рядки, сума, спосіб оплати, ознака оплати з особового рахунку, ознака поповнення рахунку, ознака підтвердження оплати рахунком, ознака оплати через термінал, виконані повернення, стан фіскалізації, ідентифікатор фіскальної картки |
| Зміни | закриті зміни від початку доби 3 дні тому за часовим поясом студії; поточна онлайн-зміна не передається |
| Розклад | заняття за 3 дні до поточного дня і 7 днів після нього, із записаними клієнтами й кількістю зайнятих місць; регулярні заняття на дати, для яких заняття ще не створено, — з поточного дня, з постійними клієнтами |
| Коди самостійного чекіну | готові QR-посилання на кожну годину наступних 48 годин: для всіх залів, для кожного залу окремо й для наборів залів, які запитує каса; лише за увімкненого самостійного чекіну; стан кодів — у полі `checkInCodesStatus` |
| Налаштування | назва й часовий пояс студії, параметри змін і запису, параметри самостійного чекіну, принтери; фіскальні й еквайрингові картки — лише ідентифікатор, назва, тип і ознака активності |

- Ключі, токени, PIN-коди касира, ліцензійні ключі й секрет підпису кодів самостійного чекіну на компʼютер каси не передаються.
- Код самостійного чекіну з даних каси збігається з кодом, який сервер приймає у відповідну годину. Код попередньої години сервер приймає ще 10 хвилин після зміни години.

### Повний пакет і оновлення

- Повний пакет містить усі дані з таблиці.
- Оновлення (запит з параметром `since`) містить усі дані, крім абонементів, категорій, товарів (назва й ціна), тренерів, залів, тренувань і налаштувань. Залишки товарів передаються в оновленні окремим списком.
- Кожен список оновлення повний: каса замінює свій список отриманим. Запис, відсутній у списку оновлення (погашений або прострочений сертифікат, оплачений або видалений борг, завершений абонемент), каса вилучає.
- Продаж товару, оплата з особового рахунку, погашення сертифіката й повернення, виконані онлайн або через застосунок, відображаються в офлайн-касі після наступного оновлення.

### Технічні параметри

| Параметр | Значення |
|---|---|
| Запит | `GET /offline/snapshot`, лише з доступом пристрою; запит лише читає дані й нічого не записує |
| Оновлення | параметр `since` — значення `generatedAt` попереднього пакета |
| Набори залів для кодів чекіну | параметр `checkInRooms`: набори через `;`, ідентифікатори залів у наборі через `,`; до 20 наборів |
| Поля відповіді | `version`, `generatedAt`, `full`, `window` (межі розкладу), `salesFrom` (початок періоду продажів), `catalog` (лише в повному пакеті), `clients`, `clientPlans`, `clientDebts`, `certificates`, `stock`, `transactions`, `shifts`, `occurrences`, `checkInCodes`, `checkInCodesStatus` |
| Заняття без створеного запису | `projected: true`, `id: null` |

| `checkInCodesStatus` | Значення |
|---|---|
| `ready` | коди самостійного чекіну передано в `checkInCodes` |
| `off` | самостійний чекін вимкнено; `checkInCodes` — `null` |
| `failed` | самостійний чекін увімкнено, коди сформувати не вдалося (зокрема, у студії ще немає збереженого публічного коду або секрету підпису кодів; їх створює перше відкриття онлайн-QR самостійного чекіну); `checkInCodes` — `null`; решта даних передається |

| Відповідь | Значення |
|---|---|
| `403`, код `DEVICE_TOKEN_REQUIRED` | запит без доступу пристрою |
| `400`, код `INVALID_SINCE` | `since` не є датою або пізніший за час сервера |
| `400`, код `TOO_MANY_ROOM_SETS` | у `checkInRooms` понад 20 наборів |

## Одноразове застосування операцій

- Кожна дія каси отримує ідентифікатор операції в момент натискання. Ідентифікатор не змінюється під час повторного надсилання.
- Дія, на яку каса не отримала відповіді сервера (обрив звʼязку, недоступний сервер), надсилається повторно з тим самим ідентифікатором — онлайн або під час синхронізації офлайн-черги. Сервер застосовує операцію не більше одного разу: повторне надсилання повертає збережений результат, другий продаж, друга оплата чи другий запис не створюються.
- Збережений результат повертається в тому вигляді, у якому його повернула перша відповідь сервера (JSON): дати — рядками ISO 8601, грошові суми — у тому самому форматі, що й у першій відповіді.
- Той самий ідентифікатор з іншим вмістом операції відхиляється.
- Операція продажу, повернення або оплати боргу, перервана після кроку, який не скасовується (рядок касового журналу, фіскальний чек), повторно не виконується. Така операція отримує результат `conflict` з кодом `OPERATION_INTERRUPTED` і потребує перевірки адміністратором. Це стосується також операції, надсилання якої не завершилося протягом 2 хвилин.
- Операція, перервана до першого такого кроку, не залишає змін; повторне надсилання з тим самим ідентифікатором виконує її.
- Операція версії, вищої за підтримувану сервером, не застосовується й дані не змінює. Операція залишається в черзі компʼютера й застосовується після оновлення сервера.
- Дія без ідентифікатора операції виконується як звичайна онлайн-дія.

Ідентифікатор операції приймають такі дії каси:

| Дія | Вид операції |
|---|---|
| Продаж, зокрема з оплатою з особового рахунку | `sale` |
| Повернення продажу | `refund` |
| Оплата боргу, зокрема з особового рахунку | `debt_payment` |
| Запис клієнта на заняття | `booking` |
| Створення клієнта | `client_create` |
| Продаж сертифіката | `certificate_sale` |
| Погашення сертифіката | `certificate_redeem` |

### Запис на заняття з ідентифікатором операції

Запис клієнта на заняття із заголовком `X-Operation-Id` і запис журналу офлайн-операцій зберігаються в одній транзакції бази: або обидва записи зберігаються, або жоден.

- Якщо запис журналу не вдалося зберегти, клієнт на заняття не записаний, сповіщення «Вас записано на тренування!» не надсилається.
- Повтор тієї самої операції (той самий ідентифікатор і той самий вміст) повертає збережений результат; повторного запису на заняття немає.
- Якщо доставка операції обірвалася до збереження, наступна доставка з тим самим ідентифікатором виконує запис на заняття заново; результат `conflict` («Потребує уваги») для такої операції не встановлюється.
- Запис у журналі змін заняття («+ Імʼя клієнта») та в історії клієнта створюється після збереження запису на заняття; помилка цих записів не скасовує запис на заняття.
- Сповіщення клієнту про запис надсилається лише після збереження запису на заняття.
- Усі записи в базу, що належать до запису на заняття, зберігаються в тій самій транзакції: перенесення повторюваного запису на інші дати цього тренування та, для неявки на персональне тренування, борг клієнта і нарахування тренеру. Якщо запис журналу не вдалося зберегти, жоден із цих записів не зберігається.
- Помилка нарахування боргу за неявку не скасовує запис на заняття; боргу й нарахування тренеру в такому разі немає.
- Помилка перенесення повторюваного запису на одну з інших дат не скасовує запис на заняття: не зберігається лише перенесення на цю дату, перенесення на решту дат зберігається.
- Сповіщення адміністратору «Звільнилося місце на тренуванні!» та записи в журналі змін заняття про перенесені дати створюються після збереження запису на заняття.
- Якщо заняття видалено до збереження запису, операція в журналі не зберігається: наступна доставка з тим самим ідентифікатором виконується заново.

### Технічні параметри

| Параметр | Значення |
|---|---|
| Заголовок онлайн-дії | `X-Operation-Id`, UUID |
| Синхронізація офлайн-черги | `POST /offline/sync`, до 200 операцій за запит |
| Поля операції | `id` (UUID), `kind`, `version`, `occurredAt` (ISO 8601), `payload` |
| Час операції | не раніше ніж за 30 днів і не пізніше ніж за 5 хвилин від часу сервера |

| Код | Значення |
|---|---|
| `IDEMPOTENCY_KEY_REUSED` | ідентифікатор уже використано для іншої операції; онлайн-дія отримує відповідь `409` |
| `OPERATION_IN_PROGRESS` | операцію з цим ідентифікатором саме застосовує інше надсилання; онлайн-дія отримує відповідь `409` з цим кодом, повторити пізніше з тим самим ідентифікатором |
| `OPERATION_INTERRUPTED` | операцію перервано після кроку, який не скасовується; повторно не виконується; онлайн-дія отримує відповідь `409`; потрібна перевірка адміністратором |
| `INVALID_VERSION` | версія операції не є цілим числом від 1; операцію відхилено |
| `RETRY` | сервер не зміг застосувати операцію; операцію потрібно надіслати пізніше |
| `INVALID_OPERATION_ID` | заголовок `X-Operation-Id` не є UUID; відповідь `400` |
| `OP_VERSION_UNSUPPORTED` | версія операції вища за підтримувану сервером; операція залишається в черзі |
| `OP_KIND_UNSUPPORTED` | вид операції сервер ще не застосовує; операція залишається в черзі |

Під час синхронізації кожна операція отримує окремий результат:

| Результат | Значення |
|---|---|
| `applied` | операцію застосовано (або застосовано раніше; повертається збережений результат) |
| `rejected` | операцію відхилено; повторне надсилання повертає те саме |
| `conflict` | операція суперечить змінам, виконаним за цей час, або її перервано після кроку, який не скасовується; потрібне рішення адміністратора |
| `retry` | операцію не застосовано зараз; її потрібно надіслати пізніше, наступні операції черги очікують |
| `in_progress` | операцію саме застосовує інше надсилання |
